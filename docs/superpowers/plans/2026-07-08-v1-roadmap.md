# V1 implementation roadmap and status control

Date: 2026-07-08

Last reviewed against repository state: 2026-07-14

## Purpose

This document tracks the current implementation status of the v1 roadmap against the live repository state.

It is intentionally based on the current repository state, not only on earlier roadmap documents. It should serve as a control document: what is implemented, what is partially implemented, and what is still untouched or placeholder-only.

## Current baseline already implemented

The repository already has the first usable installation loop for local file sources:

- `tbboot install file:<locator> --artifact <name>` resolves a `file` source, selects one artifact, writes the manifest, writes the lockfile, materializes simple `file` steps, and writes a materialization record.
- `tbboot install --declare-only file:<locator> --artifact <name>` updates only the manifest.
- Bare `tbboot install` performs a real sync path for the currently supported narrow case.
- Whole-file ownership conflicts and whole-file drift are detected and returned as user-action conflicts.
- Local `file:` sources are allowed by default only when they are inside the current operation root.
- Human output, JSON output, and exit-code classes exist for the implemented flows.
- `go test ./...` passes on the current tree when `GOCACHE` points to a writable path in the current execution environment.

That means the remaining roadmap is no longer "build the first install loop". The remaining roadmap is "expand that narrow vertical slice until it matches the documented v1 surface."

## Phase status summary

- Phase 1: partially implemented, strongest current phase.
- Phase 2: partially implemented, but only narrow `file:` trust behavior exists.
- Phase 3: partially implemented at minimal whole-file level only.
- Phase 4: largely untouched beyond placeholder commands.
- Phase 5: partially implemented at output-envelope and exit-code level only.
- Phase 6: effectively untouched.

No phase is fully complete yet.

## Remaining v1 scope and current status

### Phase 1: Finish the core install and sync model

Status: partially implemented.

Implemented now:

- Explicit `install file:<locator> --artifact <name>` works for the narrow supported case.
- `install --declare-only` persists declaration intent for one Artifact.
- Bare `install` runs a real sync path for the narrow case of one persisted declaration plus one persisted Materialization Record.
- Whole-file drift and ownership conflicts stop the operation clearly.

Still missing:

- Support more than one manifest declaration during sync. The current `Sync` path fails unless there is exactly one declaration.
- Reconcile full desired state instead of treating any extra managed artifact as an immediate removal conflict.
- Support source-scoped declarations in real command flows, not only in repository-state schema.
- Add explicit `--source-version` handling on `install`, which is part of the documented command shape.
- Decide and implement the real direct-install rules for source-level installs without `--artifact` when a source contains multiple artifacts.
- Define and implement the non-interactive removal model promised by ADR-0004, instead of stopping at a blanket conflict.

Exit condition:

- Bare `tbboot install` can reconcile a realistic manifest with multiple declared artifacts or sources and produce predictable no-op, apply, drift, and removal-required outcomes.

### Phase 2: Finish source and trust behavior promised by ADR-0002 and ADR-0003

Status: partially implemented, but only at narrow local-file level.

Implemented now:

- Local `file:` Sources are allowed by default only when they are inside the current operation root.
- Persisted `approved_sources` exist in repository-state schema and are consulted during the persisted sync path.

Still missing:

- Implement a real `git` source type.
- Add manifest-based approval flows for `git:` sources.
- Use persisted `approved_sources` consistently for explicit installs as well as sync, not only for the narrow persisted-sync case.
- Implement risky step-type allowlisting and first-install confirmation rules for `script` and `prompt`.
- Implement the **Minimum Age Rule** for source types that can prove publication time.
- Define how requested source versions interact with `git` resolution, lockfile persistence, and later sync.
- Implement "latest stable published source version" behavior where the docs promise it.

Exit condition:

- Both documented v1 source types, `file` and `git`, work with coherent trust admission, persisted approval state, and reproducible lockfile semantics.

### Phase 3: Expand materialization beyond minimal whole-file copy

Status: partially implemented at minimum viable whole-file level only.

Implemented now:

- Whole-file `file` steps materialize successfully.
- Whole-file ownership conflicts are detected.
- Whole-file drift is detected from the persisted Materialization Record.
- Rollback removes newly created files on some later persistence failures, but only as a best-effort narrow case.

Still missing:

- Implement `fragment` steps with visible fragment boundaries.
- Decide whether `template` is part of v1 or formally remove it from the v1 language.
- Implement the trust-gated execution model for `script` and `prompt` steps if they remain in v1.
- Record and surface **Recovery State** when rollback cannot be verified after partial failure.
- Harden overwrite and rollback behavior beyond "best-effort remove newly created files".
- Expand ownership rules from whole-file only to the full ADR-0004 model, including bounded fragment ownership.
- Expand drift detection from whole-file only to fragment drift where fragment support exists.

Exit condition:

- The implemented materialization model matches the step types and recovery semantics that v1 documentation claims to support.

### Phase 4: Build the missing command surfaces

Status: largely untouched.

Implemented now:

- The top-level command names and catalog subcommand names exist in CLI help.

Still missing:

- Implement `upgrade`.
- Implement `search`.
- Implement `logs`.
- Implement `catalog add`.
- Implement `catalog list`.
- Implement `catalog refresh`.
- Implement `catalog remove`.
- Add `install --upgrade` if it remains part of the documented shortcut surface.

Recommended order:

1. `upgrade`, because manifest and lockfile state already exist and the product needs a way to move forward intentionally.
2. `logs`, because real operation persistence becomes much more useful once more commands mutate state.
3. Catalog and search commands, because they broaden discovery after direct install and upgrade are solid.

Exit condition:

- `tbboot` exposes the full v1 command set from ADR-0001 with real behavior instead of `not implemented`.

### Phase 5: Finish operation reporting and log persistence

Status: partially implemented at output basics level only.

Implemented now:

- Human output exists for implemented install and sync flows.
- JSON output uses a shared result envelope with `code`, `message`, `details`, and `warnings`.
- Exit-code classes exist and are wired for success, operational error, user-action conflict, and trust-policy denial.

Still missing:

- Persist operation history under the user configuration directory.
- Implement operation scoping by operation root.
- Implement `logs` replay of the most recent operation.
- Implement `logs list` and operation lookup by operation ID.
- Add operation metadata to JSON output where relevant.
- Implement the documented verbosity model: `summary`, `normal`, and `verbose`.
- Implement the documented retention policy for recorded operations.
- Add warnings and richer summaries where trust, skipped upgrades, or deferred action matter.

Exit condition:

- Operation reporting is replayable and matches the logs and verbosity model described in ADR-0005.

### Phase 6: Complete the catalog and discovery model

Status: effectively untouched.

Implemented now:

- Command names exist in the CLI surface only.

Still missing:

- Create a persisted catalog configuration model in the user configuration directory.
- Implement catalog naming, conflict handling, and initial fetch behavior.
- Implement catalog cache storage and refresh semantics.
- Define the catalog descriptor or index contract needed for v1.
- Connect `search` to configured catalog caches.
- Connect catalog-backed install references to the main install flow.

Exit condition:

- A user can register catalogs, refresh them, search them, and install from catalog-qualified references using the same manifest and lockfile model as direct installs.

## Recommended implementation order

If the goal is to get to a credible v1 with the least churn, the order should be:

1. Multi-declaration sync and removal semantics.
2. `upgrade`.
3. Real `git` source plus manifest-based trust approvals.
4. Operation logs and verbosity.
5. Catalog and search.
6. Broader materialization types only if they still belong in v1 after a scope check.

## Items that should be reconsidered before implementation

Some documented scope may be worth cutting instead of building.

- `template` step type is named in the language but has no current implementation path or dedicated design.
- `script` and `prompt` may be too expensive for v1 unless there is a concrete near-term user need.
- Full fragment management is a real complexity jump. It should be built only if reusable repository artifacts actually need in-file insertion in v1.
- Catalog features should stay behind direct install and upgrade unless discovery is blocking adoption now.

The shortest path to a usable v1 may be to narrow v1 scope in docs before expanding the implementation further.
